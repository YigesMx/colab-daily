## 研究问题与贡献

论文《Game2Player: Scaling Gameplay Experience for Visual Agents through Environment-Player Co-Development》（arXiv:2611.24154，v1）由 UIUC、UC Santa Barbara、Georgia Tech、Northwestern 与 IBM 合作完成（Xirui Jiang、Yuxi Chen、Rui Yang、Feng Luo 共同一作等 14 位作者，Huan Zhang 项目负责人）。一句话结论：提出"环境-玩家协同开发"框架 Game2Player——Builder 智能体把现有网页游戏改造成暴露内部状态、带状态化进度与成功判定的可验证环境，Coding Player 与 VLM Player 试玩并回报缺陷驱动修复，最终以 15.7K 条轨迹（307 小时）训练出 Game2Player-9B，把 PlayerBench 进度从 14.3% 提升到 31.2%，并迁移到外部 GameWorld 基准（30.0%→53.1%）。

研究问题：游戏是视觉智能体的严格试炼场（感知、长程规划、精确控制），但获取大规模"动作+明确目标+可靠成功信号"的游戏经验很困难——人类录像昂贵，在线视频缺动作需逆向推断，现成交互环境每个游戏都要专门工程、覆盖有限。论文的思路是环境与玩家协同开发：环境缺陷往往只有真正去玩才暴露（任务不可完成、进度不更新、成功判定过早触发），玩家试玩既验证环境又顺带采集训练数据。

贡献：(1) Game2Player 框架：568 个验证过的网页游戏环境、3,436 个任务（25+ 游戏类型、7 种引擎），15.7K 条带任务指令与稠密状态进度的轨迹；(2) PlayerBench：留出 50 游戏 287 任务作为测试集，比 GameWorld 更难（各模型平均低 12.8 进度/7.6 成功分，人类也只有 69.4/51.8）；(3) 进度加权 SFT 蒸馏：Qwen3.5-9B 的 PlayerBench 进度翻倍以上并外推到 GameWorld。

## 方法与系统

环境与任务定义：可验证环境包装游戏使其可离线、按固定种子运行并在模型决策时暂停；状态 API 提供两个视图——状态探针 φ(s_t)（少量命名变量，仅评分读取）与玩家观测 ψ(s_t)（代码策略可读的屏幕可见信息，禁止隐藏信息）。任务 τ=(指令 ι, 起始例程 c, 进度函数 p, 成功谓词 g)，p/g 只读状态探针，评分无需人工或模型裁判；episode 记录最佳进度 p̄=max p_t。两个玩家：VLM Player 只看截图（游戏暂停时决策），每步输出一个动作附一句理由笔记；Coding Player 为每个游戏写一个 Python 代码策略，实时读 ψ(s_t) 游玩、不调用模型，并依据录制结果迭代代码。协同开发四阶段循环：Build（Builder 在持久会话中用引擎技能库 Unity WebGL/Flash/Godot/PICO-8 等打包游戏、写状态探针/控制指南/任务函数，任务计划冻结后不得删改放水，先自评）；Play（两玩家全任务试玩）；Report（缺陷报告：按键无效、进度不动、成功过早等；仅 Coding Player 可提观测请求：命名策略需要但读不到的量，可对照画面验证；报告不得索要隐藏信息或捷径）；Verify-then-repair（Builder 先回放录像核对报告，证据不符则驳回，否则修环境）。环境接受条件：所有报告已修复或被驳回 + 脚本门检查；代码策略接受条件：完成足量任务且每个声称完成的任务有两次成功记录。数据：1.56M 训练样本中代码策略占 87.7%、VLM 12.3%；代码策略的连续按键日志被切分为与 VLM 相同的 harness 步格式。训练：进度加权 SFT，权重 w_t ∝ ρ_t·max(1,c_t)（信用项提高进度/成功提升前最后几步的权重，惩罚项剔除或降低失败/超时/无效重复动作的权重，并对样本过多的游戏降权），随机舍入为整数倍率重采样；冻结视觉编码器微调 Qwen3.5-4B/9B 各一 epoch 9,237 步、lr 1e-5 余弦衰减。

## 实验设置与数据

数据来源 itch.io、Newgrounds 等门户；518 游戏用于训练、50 游戏 287 任务留作 PlayerBench（覆盖 7 引擎 4 难度层）。外部基准 GameWorld（34 浏览器游戏 170 任务、状态化评分、与本文集合无重叠），用本文 harness 评测。评测协议：每任务一次尝试、固定种子、温度 1、最多 100 步（游戏暂停决策）；开源模型看 50 步文本历史 + 6 张历史截图，API 模型给全量文本历史；指标为 Progress（按游戏等权的平均 episode 进度）与 Success。对比：人类玩家（15 名首次参与者实时游玩）、闭源模型（GPT-6.1 Sol/Terra、GPT-6 Luna、Claude Opus/Sonnet/Haiku 5.5、Gemini-3.8-Flash）、开源模型（DeepSeek-V4.1-Flash、GLM-5.3-Flash、Qwen3.8 系列）与游戏专用模型（PLAYER-1、GameScaling-9B）。协同开发消融：同一批 20 游戏 145 冻结任务在完整循环/无报告/通用智能体三设置下由审计模型逐任务核查（人工复核其判定）。

## 结果、限制与结论

论文报告：协同开发消融中，通用编码智能体 145 任务中 120 个环境不正确、仅解决 1 个任务；加玩家报告后不正确环境 51→40、解决任务 34→46（GPT-6.1 Sol 作 Builder 时解决任务 62→82），典型修复如"There Is No Game"进度卡 0.9 修复后 9/9 任务正确且解决。成本：报告使每游戏模型成本 +20%（$17.7→$21.3）；代码策略写一次 $10.8 后每小时游玩仅 $0.13（VLM Player 为 $54.7/小时），12 分钟后即更便宜；代码策略每小时墙钟录 7,775 步，VLM 仅 354 步（22 倍）。主结果：Game2Player-9B 在 PlayerBench 31.2 进度/15.0 成功、GameWorld 53.1/29.4，为 10B 以下开源最佳、超过 PLAYER-1-9B（19.0/7.0 与 34.5/15.9）与 GameScaling；Qwen3.5 基座 4B/9B 进度分别 15.9/14.3→31.1/31.2（约翻倍），GameWorld 增益超 20 分；在 GameWorld 上超过 Qwen3.8-Flash、GLM-5.3-Flash、GPT-6 Luna、Claude Haiku 5.5，接近 Claude Sonnet 5.5；闭源最强在 PlayerBench 约 60 进度，差距仍大。训练让思考变得有用：训练前思考开关影响 ±3 分内且方向不一，训练后 PlayerBench +7.7/+2.6、GameWorld +14.6/+19.2。消融：仅 VLM 数据样本效率高（0.19M 样本 4B 即 25.1 进度），仅代码策略数据在 GameWorld 最好（精确计时的按键/长按可迁移）；两者结合给 9B 最佳 PlayerBench（28.6 vs 25.6/20.1）；进度加权优于均匀采样（9B PlayerBench 23.9→28.6）；数据量 100K→1.56M 单调收益。案例显示训练教会了精确时序控制：Give Up 平台跳跃中 4B 从 12.3% 进度到 92.5%（47% 按键显式设置保持时长 vs 基座 1%）。

限制（论文自述）：接受的环境不保证正确（无全量人工审计；协同开发研究中 GPT-6.1 Terra Builder 任务 72% 正确、Sol 94%；PlayerBench 全部 287 任务人工复查未发现环境或评分错误）；管线仅覆盖单机离线网页游戏，在线、多人与大型商业游戏的授权与运行约束未解决。数据与环境全部来自公开网页游戏的授权边界、以及向 3D/商用游戏扩展的成本，当前材料未确认。
