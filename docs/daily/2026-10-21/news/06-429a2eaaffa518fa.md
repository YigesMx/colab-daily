## 事件概述

Anthropic工程团队于其官方博客claude.dev发文《How the Claude Code team does code review》，披露Claude Code当前的代码生产与审查体系：发布方称Claude已写下Claude Code自身约90%的代码，而代码审查的大部分阅读工作也由机器完成，人工注意力被重新配置到风险最高、最需要判断力的环节。新智元10月20日以"Claude Code自产自审：九成代码不再经过人类"为题进行了报道。官方博客原文与新智元报道页面均已抓取留存。

## 已确认事实与证据

发布方在官方博客中给出的关键事实包括：在Anthropic主代码库中，每日落地的改动数量从今年5月的约2,500次增至9月的30,000次以上；Claude Code使用独立代码库，同样面临高速合入压力。从6月到9月，Claude Code代码库合入的拉取请求（PR）数量翻倍以上，而需要回滚的比例下降超过40%。官方将此归因于分层检查体系而非单一人审关卡：PR提出前，Claude自行运行测试、构建与代码检查工具，另一智能体以全新上下文复审改动差异；每个PR必须通过强制CI（代码风格、类型、测试）；AI缺陷审查由多个智能体分头查找问题，再由另一组智能体投票筛选，未获足够票数或仅涉及风格的意见不予发布——该功能研究预览版上线后，获得实质性审查意见的内部PR占比从16%升至54%；每条意见带"Important""Nit"或"Pre-existing"（既有问题）标签，后者用于澄清问题并非本次改动引入；安全审查独立进行，缺陷审查或安全审查存在未决发现时PR不得合并。审批环节采用基于风险的分级：由分类器根据改动本身（而非提交者）判定需要零人、一人或两人批准，部分路径始终需要人工；官方明确"智能体的批准永远不算作人的批准"，触发智能体编写改动的人须计入审批责任；合入经合并队列在最新主分支上重跑检查，合并后由功能开关与快速回滚兜底——官方图示将其概括为"六层检查，其下为回滚"（新智元报道表述为七层，口径略有差异）。关于审查收敛，官方披露了一个案例：一个CLI项目的PR由智能体作者与智能体审查者在一夜之间往复了50多轮修改与审查才被其所有者手动叫停；对审查者反复标记内容进行git blame追溯后发现，约59%的问题在首轮审查时就已存在。此后团队将审查轮数限制在最多三轮：一轮即通过的PR占比从65%升至78%，平均审查轮数从2.08降至1.32，需要五轮以上审查的PR占比从8.9%降至1.5%。官方同时说明人的新角色：判断改动"该不该做"而非逐行阅读；计费、自动更新器、CI等高风险代码路径，以及可能被他人当作模板抄用的架构设计，仍保留人工审查；仓库受信任名单之外提交的改动需要第二人批准。

## 影响与后续观察

这组数据为"AI写、AI审、人把关风险"的工程范式提供了一个高吞吐真实样本：在改动量增长12倍的情况下回滚率反而下降，说明显式分层验证与基于风险的审批可以替代部分人工阅读而不牺牲质量底线。对行业而言，其参考价值在于把审查问题从"人看没看过"重构为"这道改动会怎么出事、由哪道检查拦截"，以及用轮数上限与意见分级控制智能体间的审查振荡。后续值得观察：该体系在Anthropic主代码库之外的开源协作场景是否可复制；"智能体批准不算数"与风险分级能否成为行业规范；智能体间50多轮审查振荡的根因（Nit类意见的自动修复循环）是否有更系统的抑制机制；以及外部贡献者与内部流程的差异化治理。新智元报道中"90%代码由Claude编写"出自官方博客原文，其余如具体案例细节均与官方博客一致。
